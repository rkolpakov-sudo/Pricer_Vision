# План: редактируемые группы товаров (категории) в UI

> **Статус: реализовано** (этапы 1-5). Код: `src/graph_engine.py`, `src/memory_manager.py`,
> `src/config_loader.py`, `src/ductwork_calculator.py`, `src/agent_loop.py`,
> `gui/graph_assistant.py` (страница «Категории» + `SplitTypeDialog`), `config/settings.yaml`
> (`special_types`). Ниже — исходный план (контекст и матрица влияния).

## 1. Проблема (что не может пользователь)

Пользователь не может из UI вынести часть товаров (напр. «Изоляция для труб») из общей группы
«Инструменты, крепёж, изоляция, защитные покрытия» в отдельную группу/тип:

- **Групп как сущностей нет**: ни таблицы, ни модели, ни CRUD. «Группа» = только ключ в
  `product_types.category` (или ключ `category_map` в YAML). Листовые группы (`tools_general`,
  `fire_safety`) вообще являются типом, чей `id == category` и чей `name` = русский заголовок группы.
- **Тип можно создать/переименовать/удалить** (`gui/graph_assistant.py:611-764`, ProductTypePage),
  но «прикрепить тип к группе» = просто текстовая строка «Категория (опц.)»; списка групп, переименования
  группы, переноса товаров между группами — нет.
- **Источник истины — `config/categories_and_sites.yaml`** (`category_map`, `priority_order`), который
  перезаливается при старте/`_reload_yaml` (`load_yaml_seed`, `graph_engine.py:686-744`, INSERT OR REPLACE).
  Изменение из YAML — «чёрный ящик»: непонятно, что сломается.

## 2. Как устроена иерархия (факт)

| Понятие | Где живёт | Пример |
|---|---|---|
| Группа/категория | только ключ `category_map` в YAML + `product_types.category` | `tools_general`; заголовок «инструменты, крепёж…» = `focus`/`name` |
| Тип | строка `product_types(id, name, category, keywords)` | `plumbing_heating_pipes`, `tools_general` |
| Связь тип→сайт | `product_sites(product_type_id, site_id, priority)` (+ `concept_edges SOLD_AT`) | santech.ru → plumbing_heating_pipes |
| `sites.group_name` | мёртвая колонка (0 строк) | — |

Ключевой инвариант пайплайна: **всё ключуется по `product_types.id` (строке)**, а не по имени/группе:
approaches/hints/concepts/confirmed_prices `product_type_id`, `product_sites`, SessionFacts
`{тип}|{бренд}`, `site_profiles.json`, жёсткие ворота `_RADIATOR_PRODUCT_TYPES` /
`_VENTILATION_PRODUCT_TYPE`, контекст/системный промпт, `_resolve_product_type`.

При этом `classify_product_type` работает **только по keywords** (субстроки), `category` не читает;
список сайтов — по `product_sites[тип]`, `category` не читает. Значит:

> **Перенос типа в другую группу (смена `category`) — безопасно на 100%: рантайм этого поля не читает.**
> **Опасно только: (а) переименование/создание ТИПА-ида (осиротение дочерних таблиц без миграции);
> (б) сплит товаров на новый тип (classify перестанет их отдавать старому; новый тип останется без сайтов/подходов/памяти).**

## 3. Матрица влияния изменений (что заденет «весь остальной пайплайн»)

### 3.1 Безопасно (метаданные, рантайм не читает)
- Переименование `category` типа; переименование русского заголовка группы; порядок групп.
- Добавление сайта к типу (SitePage уже умеет).

### 3.2 Меняет поведение (нужно осознанно + миграция/переобучение)
| Изменение | Что произойдёт | Где |
|---|---|---|
| Новый тип-ид из сплита (изоляция) | classify больше не вернёт старый `tools_general` для изоляции; новый тип пуст: нет `product_sites` (целевой сайт → yandex fallback), нет approaches/hints/SOLD_AT, нет SessionFacts, нет site_profiles | classify `graph_engine.py:669-682`; get_sites `:602-604`; task_scheduler `:64-99` |
| Переименование существующего типа-ида | Осиротеют approaches/hints/confirmed_prices/product_sites/concept_edges + SessionFacts + site_profiles (нет каскада по id) | все точки из §2 + изучение-отчёт (22 файла) |
| Сплит у радиаторов/воздуховодов | `_RADIATOR_PRODUCT_TYPES={"plumbing_heating_radiators"}`, `_VENTILATION_PRODUCT_TYPE=...ventilation` — калькуляторы молча отключаются | `agent_loop.py:43,1783`, `radiator_section_pricer.py:20`, `ductwork_calculator.py:146` |
| YAML-перезаливка | INSERT OR REPLACE перезапишет id/name/category/keywords для сид-типов; пользовательские типы (id не из YAML) переживают | `load_yaml_seed` |

### 3.3 Не зависит от типа (не ломается)
rule-8 reuse (`get_confirmed_prices` — по токенам spec), SemanticCache (md5 spec), NegativeCache,
SiteBlacklist, Audit, approach_relevance (токены), ExcelWriter/column_classifier (spec без типа).

## 4. Целевой рефакторинг (этапы)

Принцип: **группы — полноценная редактируемая сущность; тип-ид — стабильный ключ; сплит идёт
через «мастер», который сам разводит сайты/память; миграция при переименовании ида — обязательна.**

### Этап 0 — Безопасные низкорисковые шаги (независимы, делаем сразу)
1. `sites.group_name` — убрать или задокументировать как мусор (не трогаем, чтобы не плодить изменений).
2. `src/_labels.py` дополнить недостающими RU-метками (если сплит добавит новую категорию/тип — вывод
   в Excel/«Категория» не должен показывать сырой id).

### Этап 1 — Категории как сущность (модель + CRUD, без UI)
1. Таблица `categories(id TEXT PK, name TEXT, priority INT, focus TEXT, created_at)` (миграция в
   `graph_engine._init_db`).
2. `load_yaml_seed`: дополнительно импортировать `category_map` в `categories` (INSERT OR REPLACE).
3. Engine/MemoryManager API:
   - `list_categories()` / `save_category(id, name, priority, focus)` / `rename_category` /
     `delete_category(id)` (удаление только пустой — нет типов; иначе error).
   - `set_product_type_category(type_id, category_id)` — ТОЛЬКО `UPDATE product_types SET category`
     (без трогания name/keywords; рантайм-безопасно).
4. Классификация остаётся на keywords (не трогаем поведение на Этапе 1).

### Этап 2 — UI управления категориями и переноса типов
1. Новая страница «Категории» в `gui/graph_assistant.py` (AssistantToolPanel.TOOLS):
   - таблица категорий (id, RU-имя, приоритет, число типов);
   - создать/переименовать/удалить категорию;
   - вложенный список типов с кнопкой «перенести в категорию» (комбобокс категорий) →
     `set_product_type_category`.
   - Пометить, какие типы/категории пришли из YAML (source=yaml), какие созданы пользователем.
2. `ProductTypePage`: заменить текстовое поле «Категория» на комбобокс существующих категорий
   (editable для нового), чтобы создание типа всегда попадало в валидную группу.
3. Обновлять комбо «Тип товара» и страницы после изменений (`refresh_combo`/`_refresh_combos`,
   graph_assistant.py:1994-2010, 1907-1914).

### Этап 3 — Сплит товаров на новый тип (мастер «вынести в отдельную группу»)
UI-операция: «взять N товаров из типа A → новый тип B под категорией C».
1. Создать тип B (id по паттерну `{category}_{slug}`) с keywords, отобранными для отделяемых товаров;
   **удалить эти keywords из A** (иначе tie-break/первый-в-словаре может вернуть A).
2. **Сайты**: мастер предлагает стартовый список = сайты A (копия product_sites) + возможность
   править через SitePage (у специализированных сайтов по изоляции это будут другие сайты —
   пользователь сам добавит; автоузнавание как раньше: `save_discovered_site`).
3. **Память**: подходы/цены/хинты переносятся из A в B, только если `approach_relevant` по новым
   keywords согласен (иначе мусор из общей группы не тащим в специализированную).
4. Указать тип B в `_RADIATOR_PRODUCT_TYPES`/`_VENTILATION_PRODUCT_TYPE`-аналогах? — вынести эти
   «ворота» из захардкоженных строк в конфиг `settings.yaml` (список типов радиаторов / тип вентиляции),
   чтобы сплит не молча отключал калькуляторы.

### Этап 4 — Безопасное переименование типа-ида (миграция)
Если пользователь переименовывает id типа — выполнить миграцию дочерних данных:
`approaches.product_type_id`, `confirmed_prices.product_type_id`, `hints.product_type_id`,
`product_sites.product_type_id`, `concept_edges.child_name` (SOLD_AT), затем пере-классификация
site_profiles/SessionFacts недоступна (они вне БД) — их старые ключи помечаем устаревшими/сбрасываем
с предупреждением. Иначе — **запретить смену id** (оставить только переименование `name`, как сейчас),
а «переезд товаров» делать только через мастер Этапа 3 (без осиротения).

Рекомендация: **Этап 4 = запрет смены id + мастер Этапа 3** (не делать миграцию id — слишком хрупко).

### Этап 5 — Согласование с YAML
При `_reload_yaml`: категории/типы пользователя (source != yaml, отсутствуют в YAML) не удаляются;
предупреждение, если YAML перезаписал пользовательские name/category/keywords сид-типа.

## 5. Минимальный вертикальный срез (рекомендуемый объём первой итерации)

Задача пользователя (изоляция → отдельная группа) решается безопасно без переименования идов:

1. **Этап 1** (таблица categories + CRUD + импорт из YAML) — модель.
2. **Этап 2** (UI «Категории»: создать категорию «Изоляция для труб», перенести в неё тип
   `tools_general`... — нет, стоп: изоляция сегодня НЕ отдельный тип).

Уточнение среза: изоляция не имеет своего типа-ида. Чтобы «вынести в отдельную группу», нужен
**сплит** (Этап 3): создать тип `tools_general_pipe_insulation` (keywords: изоляц, Energoflex, K-Flex,
XOTPIPE, теплоизоляц, цилиндр …), убрать эти keywords из `tools_general`, скопировать сайты-старт,
перенести подтверждённые цены/подходы по изоляции. Поэтому минимальный полезный срез = **Этап 1 + 2 + 3**;
Этап 4 — запрет смены id; Этап 5 — защита от YAML-перезаписи.
