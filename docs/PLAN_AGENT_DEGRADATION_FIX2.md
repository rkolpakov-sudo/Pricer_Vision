## 0. КРИТИЧЕСКОЕ — П3: реюз не должен путать модели/типы (C10 vs C20)

### Факт (лог 27.08, строки 16–23)
Агент вернул из кэша цены C10-товаров для C20-товаров (наименования почти
идентичны, но C10 и C20 — РАЗНЫЕ радиаторы):
- Row 16: 4044.15 (C10 500×600) → rule-8 реюз за 0.0 с;
- Row 18: 4845.25 (C10 500×800) → rule-8 реюз;
- Row 19: кэш 5288.69 (C10 500×900), similarity 0.83;
- Row 20: 5771.03 (C10 500×1000) → rule-8 реюз;
- Row 21–23: 6217.30 / 6660.83 / 7107.11 (C10) → кэш/реюз для C20.
Row 17 (C20 500×700) уцелел только потому, что C10-цена 500×700 была ещё 0.50.

### Корневая причина (воспроизведено кодом)
```
_is_optional_token('c10') → True   # любой токен с цифрой — «опционален»
missing_required_tokens(C20 spec vs C10 stored) → []
_size_key(C20 spec) == _size_key(C10 stored) == {'500x600'}
product_name_matches(C20spec, C10stored, strict_sizes=True) → True  # ОТРАВЛЕНИЕ
```
- `_is_optional_token` (`approach_relevance.py:387-398`): `bool(re.search(r"\d", w))` →
  ЛЮБОЙ токен с цифрой опционален. Модельные коды «c10»/«c20»/«vc33»/«ms140»
  выпадают из `required` в `missing_required_tokens`.
- Оба пути реюза используют этот матчер: `graph_engine.get_confirmed_prices`
  (rule-8, `graph_engine.py:445-447`) и `semantic_cache.get_similar`
  (`semantic_cache.py:55-56`).
- Особенность прогона 27.08: C20-цены НЕ создали отдельных записей — dedup в
  `save_price` (`memory_manager.py:210-218`) записал C20-цену в C10-запись того же
  размера (1 повреждённая запись: C10-spec 500×700 с ценой C20 6861.10).

### Решение (Фаза 0 — блокирующий фикс)
0.1 **`model_designators(text)`** — РЕАЛИЗОВАНО (`approach_relevance.py`):
  «C10», «C 10», «VC33», «MS-140» → «c10», «vc33», «ms140»; исключены префиксы
  параметров/диаметров и разделитель «х». Проверено на корпусе.
0.2 **`product_name_matches(..., strict_sizes=True)`** — РЕАЛИЗОВАНО: равенство
  моделей обязательно на путях реюза И гида (strict_sizes/ignore_sizes).
  C20-spec vs C10-stored → False.
0.3 **Гид (ignore_sizes)** — РЕАЛИЗОВАНО (та же проверка 0.2).
0.4 **Advisory/`mismatch_kind`** — РЕАЛИЗОВАНО: модель — ключевой дифференциатор
  на СЫРОМ тексте (h1 «C 10х500х600» токенизатор не видит «c10»); материал
  («стальной») — описательный; размер/бренд — ключевые. В капе confidence
  (`agent_loop.py`) `descriptive_only` → не режется до 0.5.
0.5 **Очистка БД** — РЕАЛИЗОВАНА: бэкап `data/pricer_backup_20260827_pre_p3.db`,
  удалена повреждённая запись id=1818 (C10-spec 500×700 с ценой C20 6861.10);
  семантический кэш не содержит C20-ключей (реюз не писал в кэш) — матчер закрывает
  неверные чтения.

## 3. Фаза 1 — вернуть реюз точных цен прошлых прогонов (П1)

### 1.1 Различать тип расхождения при капе confidence
**Файлы:** `src/approach_relevance.py` (helper `mismatch_kind`), `src/agent_loop.py:872-876`.
- Helper `mismatch_kind(spec_text, found_name) -> str`:
  `"none"` / `"descriptive_only"` / `"key"`.
  - Сначала модель (сырой текст, `model_designators`): у spec есть модели и они
    ≠ моделям found → `"key"` (C20-vs-C10 → кап 0.5 сохраняется, даже если описательные слова совпадают).
  - Затем описательные слова через `missing_required_tokens` + `_OPTIONAL_SET`
    (механизм уже есть в `_mismatch_warning_content:1623-1626`).
- В ветке капа (`agent_loop.py:872-876`):
  - `descriptive_only` или `none` → **НЕ капить**: `confidence = max(llm_conf, 0.8)`, `requires_review=True`;
  - `key` (модель/тип/материал/соединение/бренд) → прежний кап 0.5.
- Эффект: LEMAX-C10 (расхождение только по «Compact Hygiene/в компл./боковым», модель C10=C10)
  → 0.8+ → rule-8; C20-vs-C10 → кап 0.5, защита от отравления.
- [x] РЕАЛИЗОВАНО (в рамках Фазы 0, `mismatch_kind` + кап в agent_loop). Тесты: кап
  descriptive_only ≥0.8, модель C20≠C10 → 0.5, `mismatch_kind` для LEMAX/Ду.

### 1.2 Точное совпадение spec_text = доверенное (rule-8)
**Файл:** `src/agent_loop.py:411-434`.
- В rule-8: если кандидат имеет `spec_text`, нормализованно (lowercase+схлопывание) **равный**
  текущему, URL — валидная карточка (не homepage/search/family), `is_stale=False` →
  разрешить реюз при `confidence >= 0.6` (вместо 0.9). Кап 0.5 защищал от перекоса
  «Изоляция Ø25 vs Трубка» — там строки разные, точное совпадение исключает этот риск.
- ⚠️ **Жёсткая зависимость от 0.5**: poisoned-записи (C20-спец с C10-ценой, conf 0.90)
  имеют spec_text, РАВНЫЙ будущим C20-строкам — без очистки 0.5 они станут реюзными
  по 1.2 ещё активнее. Порядок: 0.5 → 1.2.
- [x] РЕАЛИЗОВАНО: `_normalized_equal` + `reuse_threshold = 0.6` при точном совпадении
  (не stale) в rule-8. Тесты: exact-spec conf 0.6 → реюз без браузера; сосед → нет.

### 1.3 Одноразовая миграция данных
- Скрипт: поднять `confidence 0.5 → 0.8` для записей с модельным кодом в spec_text,
  валидным URL карточки и reason без негативных маркеров (не соответств/другой/…).
- [x] ВЫПОЛНЕНО: бэкап `data/pricer_backup_20260827_pre_p1.db`, повышено 18 записей
