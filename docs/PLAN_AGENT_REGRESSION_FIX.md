Статус: сформирован, ждёт утверждения

## 1. Контекст и симптоматика (лог 11:20, прогон 151 позиции)

Позиция 36 (Чугунный секционный радиатор МС-140) деградировала:

1. Агент НЕ использовал кэш по МС-140 (в БД есть #1846: santech 5636.8 ₽, conf 0.95).
2. Начал поиск на satro-paladin.com (где МС-140 отсутствует), хотя santech имеет цену.
3. Ввёл запрос, сообщил о необходимости очистки поля, не очистил — ушёл дублированный
   запрос «МС-140 Мх500МС-140».
4. Минутами бездействия в результатах поиска (11:24:58 → 11:29:47 = ~5 мин).
5. Перешёл в карточку «ЦМО МС-40» (полка для шкафа, НЕ радиатор) — 4 раза сообщил,
   что это неверный товар, и не двигался дальше.
6. Упёрся в жёсткий лимит 900с (Row hard cap) — строка провалена.

## 2. Корневые причины (по приоритету)

### P1. Кэш/rule-8 МС-140 мёртв из-за кириллического «х» (КЛЮЧЕВАЯ)
- `model_designators()` сравнивает наборы моделей СТРОГО (approach_relevance.py:588-591).
- Для МС-140:
  - spec: `{'мс140', 'мх500', 'мx500'}` — «МС-140 Мх500-0,9-2» → кириллическое «мх500»
  - stored (#1846): `{'мс140', 'мx500'}` — «МС-140 Мx500» → латинское «мx500»
- Наборы НЕ равны → `product_name_matches` False → rule-8 и гид не видят #1846.
- `_MODEL_CODE_RE` собирает «мх500» как префикс «мх» (не исключён), «х»/«x»/«×» не
  нормализованы. Это НЕ регрессия последнего коммита — логика Фазы 8, но она делает
  кэш МС-140 нерабочим.

### P2. Рейтинг сайтов по типу смешивает модели радиаторов
- `success_scores[site] = Σ success_count` подходов ПО ТИПУ `plumbing_heating_radiators`.
- satro-paladin: 56 (LEMAX-радиаторы), santech: 1 (МС-140).
- Рейтинг толкает агента на satro-paladin, где МС-140 нет. Нужно ранжировать по
  (тип, модель) — модель из `model_designators(spec_text)`.

### P3. Агент следует подходу satro-paladin (input.search_input), где товара нет
- Следствие P2: первый сайт = satro-paladin → агент следует его подходу → застревает.

### P4. Дублирование запроса на SPA-сайте
- Агент очистил поле через JS (`inp.value=''` + dispatchEvent), но digiSearch (SPA)
  не сбросил внутреннее состояние — текст склеился «МС-140 Мх500МС-140».
- Нет проверки результата очистки и нет правила в промпте.

### P5. Переход в нерелевантную карточку (ЦМО МС-40 = полка)
- Агент открыл карточку 67422 без проверки названия в выдаче (нарушение правила 20).
- LLM (very-low 27B) принял «МС-40» за аналог «МС-140».
- Нет кода-гейта: не открывать карточку, если модель из выдачи не совпадает с
  моделью спецификации.

### P6. Долгие паузы в результатах (5 минут)
- Контекст разросся до 7800+ токенов; вызов very-low 27B занимает 30-60с.
- StuckDetector не прерывает: LLM «думает вслух» без новых tool_calls.

### P7. Зацикливание LLM (повторы выводов разными словами)
- Агент 4 раза сообщил «ЦМО МС-40 = полка», не вызывая инструментов.
- StuckDetector отслеживает tool-действия; «мысленный цикл» без инструментов не
  распознаётся.

## 3. План исправлений (фазы)

### Фаза 1 — Нормализация «х»/«x»/«×» (P1, критично)

**Файл:** `src/approach_relevance.py`

1. Добавить нормализацию перед извлечением моделей и размеров:
   - `_normalize_homoglyph(text)`: заменить «×» и кириллическую «х» на латинскую «x»
     только в контексте размеров/моделей (не трогать слова «характеристика»).
   - Безопасный подход: нормализовать «х»→«x», «×»→«x» глобально в
     `model_designators` и `_size_key` (перед regex). Риск: слово «характеристика» →
     «xарактеристика» — не токенизируется, т.к. «xа...» не модель (префикс «xa» не
     в интересе, но может попасть в _product_tokens). Ограничить: замена только там,
     где «х»/«×» стоит МЕЖДУ цифрами или цифрой и буквой (паттерн размера «500х600»).
   - Реализация: `_norm_dims(text) = re.sub(r'(?<=\d)[х×](?=\d)', 'x', text)`;
     дополнительно в `model_designators` перед regex.
2. Тест: spec «МС-140 Мх500-0,9-2» vs stored «МС-140 Мx500 (…МС-140х500)» →
   `model_designators` равны, `product_name_matches(ignore_sizes=True)` = True.

**Проверка:** `get_relevant_prices('Чугунный…МС-140…', ignore_sizes=True)` вернёт #1846.

### Фаза 2 — Рейтинг сайтов по (тип, модель) (P2, P3)

**Файлы:** `src/agent_loop.py` (`_build_context._sort_key`), `src/learning_loop.py`
(`rank_sites`), `src/mcp_agent_runner.py` (`_site_ranking_for`)

1. `_sort_key`: считать `success_scores` по подходу, релевантному текущей МОДЕЛИ:
   - `model = model_designators(spec_text)`
   - `success_scores[sid] = Σ success_count` подходов, где
     `model_designators(a.search_query) ∩ model` не пусто (модель совпадает).
   - Подходы LEMAX (модель «lemax») не влияют на рейтинг МС-140.
2. `_site_ranking_for` в runner: передавать модель в `rank_sites`.
3. Тест: santech (МС-140) выше satro-paladin (только LEMAX) для запроса МС-140.

### Фаза 3 — Очистка поля на SPA перед вводом (P4)

**Файл:** `src/agent_loop.py` (SYSTEM_PROMPT правило), возможно
`src/site_analyzer.py`

1. Правило в промпт: «Перед browser_type в поисковое поле SPA-сайта: очисти поле
   через JS (set native value) и ПРОВЕРЬ результат (value==''), только затем вводи».
2. Опционально: в обработчик `browser_type` добавить автоматическую очистку, если
   сайт помечен SPA (`SiteAnalyzer`).

### Фаза 4 — Гейт перехода в карточку по модели (P5)

**Файл:** `src/agent_loop.py` (обработка browser_click/navigate на карточку)

1. Если агент наводится на карточку (URL `/catalog/product/…` или клик по элементу
   с названием) И `model_designators(название_элемента)` НЕ пересекается с
   `model_designators(spec)` И известна модель — вернуть error: «карточка не
   соответствует модели спецификации (МС-140), не открывай».
2. Достаточно мягкого предупреждения (LLM решает), не жёсткого блока — см. принцип
   «система-советник». Но при явном несовпадении модели — совет жёстче.
3. Тест: «ЦМО МС-40» (полка) не предлагается как карточка МС-140.

### Фаза 5 — StuckDetector для «мысленных циклов» (P6, P7)

**Файл:** `src/stuck_detector.py`, `src/agent_loop.py`

1. В `process_row`: отслеживать «бездействие» — N раундов подряд без новых
   tool_calls (только content-размышления) при одном и том же `price_candidate_seen`
   состоянии → добавить диагностическое сообщение «ты не двигаешься: либо извлеки
   цену/перейди в карточку, либо переключи сайт».
2. Порог: 2 раунда подряд без tool_calls → reminder; 4 → force (совет).
3. Тест: симуляция серии content-only ответов → reminder добавляется.

### Фаза 6 — Снижение времени на выдачи (P6, вспомогательное)

**Файл:** `src/agent_loop.py`

1. Не дублировать извлечение: если в выдаче УЖЕ извлечены названия+цены, и LLM
   повторно вызывает тот же browser_evaluate с тем же JS на том же URL —
   вернуть кэш-ответ (в рамках строки) и подсказать.
2. Сократить объём context: лимитировать `content_to_send` для browser_snapshot на
   страницах выдачи (уже есть `_clean_snapshot` — усилить).

## 6. Риски и митигация

| Риск | Митигация |
