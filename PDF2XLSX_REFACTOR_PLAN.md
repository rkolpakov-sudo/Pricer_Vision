## 0. Цель (одним абзацем)

Приложение Pricer Vision получает на вход **полный проект в формате PDF**, по методологии Hermes-инструментария **выявляет в нём спецификацию**, обрабатывает её (классификация строк, полное наименование, чистка) и **конвертирует в XLSX с форматированием, как делает Hermes**. Дальше этот XLSX — уже готовый, «переработанный» продукт — **парсится штатным загрузчиком приложения** (`load_spec` + `column_classifier`), и с ним работает обычный конвейер сбора цен. Внешние элементы интерфейса (кнопка «📄 Загрузить PDF», прогресс, ревью) **не меняются** — меняется суть: Pricer Vision больше не «парсит PDF по-старому», он **обрабатывает PDF так же, как это делает Hermes, под управлением той же LLM**, а парсит уже готовый XLSX.

## 2. Эталон: как устроен Hermes-инструментарий под управлением LLM

### 2.1 Состав инструментария (реальные артефакты, изучены)

| Skill | Роль | Ключевые артефакты |
|-------|------|--------------------|
| `spec-pdf-csv` | Ядро для спецификаций ВК/СО | `SKILL.md` (методология + pitfalls), `scripts/extract_spec.py` (418 стр., детерминированный конвейер CLI) |
| `pdf-table-to-csv` | Обобщённая методология таблиц | `references/domain-notes.md`, `references/hierarchical-parent-child-rows.md`, `scripts/qa_scan_csv.py` |
| `ocr-and-documents` | Сканы/OCR | лёгкий стек: pymupdf, marker-pdf |

### 2.2 Механика работы под LLM (что именно надо пересоздать)

Инструментарий работает в **два слоя**, и эффективность даёт связка:

1. **Детерминированное ядро** — `extract_spec.py` (и скрипты QA). Без LLM выполняет:
   - `extract_records()` — извлечение таблиц через `page.find_tables().extract()` (PyMuPDF; корректен на повёрнутых 90° листах);
   - `find_spec_header()` / `spec_header_score()` / `map_columns()` — **детекция границ спецификации внутри большого документа проекта**: страница/таблица принимается как спецификация только если шапка маппит **≥6 из 9 логических колонок** (`poz, name, type, code, supplier, unit, qty, mass, note`); экспликации узлов (score 3), ведомости помещений (score ≤4), штампы рамок — отбрасываются; остальные страницы проекта игнорируются;
   - `classify()` — классификация каждой строки: **item** (есть кол-во) / **header** раздела (префиксы HEADER_PREFIXES: Водопровод, Трубы и изоляция, Канализация, Оборудование, … или `[ВТК]\d`) / **component** состава комплекта (свой ГОСТ/ТУ) / **continuation** (размер/атрибут → слияние с предыдущей позицией) / **групповая строка** (пустое имя + type + qty → наследование имени предыдущей позиции, `GROUP_INHERIT`);
   - **правило полного наименования** (требование пользователя): материнская строка-описание БЕЗ количества **поглощается** своими дочерними позициями (ребёнок с пустым именем → `name := мать`; ребёнок с коротким обозначением DN15/LEMAX… → обозначение в «Тип, марка»); мать С количеством остаётся позицией и открывает группу; структурные подзаголовки («Система К1:», `^П\d+$`) — не матери; нумерация «с пропусками» — ожидаема (`MOTHER_ABSORBED / FULL_NAME_CHILD / FULL_NAME_INHERIT`);
   - **очистку текста** `clean_text()`/`clean_name()`: разорванные слова (SPLITS: «Труб а→Труба»…), **Ø-коррупция** шрифтов (токен-правило `6<диаметр>х<толщина<100>` → Ø, `ф`/`∅`→Ø; НЕ трогать `650x400`, `DN160`, `Ду=65`), разделитель «х», склейка `ТУ -2248- 043-…`, мягкие переносы в шапке, `B1 .3→B1.3`; ОВ-фитинги без слова «стальной» → добавить («Отвод-45 стальной», «Заглушка стальная …»);
   - `qa()` + `qa_scan_csv.py` — контроль: orphan=0, двойные пробелы, `[\w]\s[.,:;]`, голый `Ø`, остатки split-слов;
   - вывод: `spec_<base>_log.json` (журнал каждого MERGE/HEADER/COMPONENT с фрагментом и страницей), `final_rows.json`, CSV `utf-8-sig`, разделитель `;`.

2. **LLM-оркестратор (агент Hermes)** — цикл поверх ядра:
   - разведка (кол-во страниц, повороты, наличие таблиц) → запуск ядра → **чтение логов и результатов**;
   - верификация по критериям готовности; при новых паттернах в данных — **правка правил ядра** (списки SPLITS, HEADER_PREFIXES, шаблоны) и повторный прогон;
   - точечные суждения на неоднозначных строках (заголовок vs продолжение vs мать), решение об остановке;
   - доставка: CSV + `final_rows.json` + `final_log.json`; сборка/форматирование XLSX.
   - Накопленный доменный опыт закреплён в SKILL.md (pitfalls) — **это и есть «знание», которое LLM применяет**.

> **Вывод для нас**: «полный аналог Hermes» = то же детерминированное ядро (методология выше) + тот же LLM-цикл «прогон → чтение логов → верификация → правка правил → повтор», встроенный в QThread приложения, где LLM-вызовы идут через существующий `llm_client`, а правила/журналы — файлы в `data/`.

### 2.3 «Та же LLM, что у Hermes» — что это значит технически (проверено в коде)

- `src/llm_providers.py` уже содержит реестр `Provider` с **routerai** (`https://routerai.ru/api/v1`, `auth_service_ids=("routerai",)`) и **opencode** (`https://opencode.ai/zen/v1`);
- креденшиалы парсятся при каждом запуске: **env → `~/.local/share/opencode/auth.json` → `~/.hermes/.env`** — тот же источник, что у Hermes; в проекте секреты не хранятся;
- `config/settings.yaml → llm.provider/model`; выбор провайдера и модели — через штатный SettingsDialog (`/models` + кэш), поэтому «та же LLM, что у Hermes» достигается выбором того же провайдера/модели, что настроен у Hermes (например routerai-модель, на которой работает сам Hermes), без каких-либо новых механизмов.
- Существующий `LLMClient` (retry/backoff/circuit breaker, per-call temperature/max_tokens, `force_json`) — переиспользуется.

## 3. Текущий механизм парсинга PDF в Pricer Vision (инвентарь по результатам изучения кода)

### 3.1 Фактический поток (src/pdf_parser/, main.py)

```
PDF
 └─ pdf-inspector (fast_backend.classify): pdf_type {text_based|scanned|image_based|mixed},
    confidence, has_encoding_issues, pages_needing_ocr   [~20 мс, без зависимостей]
    └─ route_pdf(): text_based ∧ conf≥0.8 ∧ ¬encoding_issues → "fast", иначе "mineru"
        ├─ fast:  GostFormParser (геометрический разбор ГОСТ-формы по координатам
        │          _pi.extract_text_with_positions: Y-кластеры строк → X-сетка колонок
        │          по маркерам «1»..«9» → сборка позиций → глобальное разрешение матерей,
        │          gate: покрытие именованных позиций ≥0.9) ── иначе ──>
        │          fast.extract_markdown (text_based) → SpecStructurer
        └─ mineru: MinerUBackend.parse_async (subprocess venv python CLI, kill-tree,
                   progress из stderr) → markdown → SpecStructurer
SpecStructurer: _html_to_text → [use_llm: one-shot JSON-структурирование (default off)]
                → _fallback_parse (regex: pipe-строки | якоря «name unit qty»/«name qty unit»,
                маркеры позиций, _STAMP_RE, requires_review-флаги)
→ FeedbackCollector.apply_corrections (SQLite data/pricer.db, пользовательские правки)
→ SmartReview (confidence ≥0.8 авто / ниже — на проверку)
→ ReviewDialog (GUI: подтверждение/правка, правки → FeedbackCollector)
→ _save_pdf_items_to_excel: 7 колонок [#, Наименование, Характеристики, Артикул,
  Изготовитель, Кол-во, Ед.]  ← ПОТЕРЯ: Позиция-номер частично, Поставщик, Масса, Примечание,
  форматирование оригинала
→ load_spec() → excel_writer.detect_columns → column_classifier → внутренняя схема
```

### 3.2 Модули (роль, ключевые точки)

| Файл | Роль | Ключевое |
|------|------|----------|
| `pdf_parser/runner.py` | QThread-оркестратор | `PdfParserRunner`; маршрутизация, stop через kill-tree, сигналы progress/items_ready/done |
| `pdf_parser/fast_backend.py` | pdf-inspector обёртка | `FastBackend.classify/extract_markdown`, `route_pdf()` — чистая функция |
| `pdf_parser/mineru_backend.py` | OCR-бэкенд | `MinerUBackend.parse_async`; subprocess `venv/Scripts/python.exe -c "from mineru.cli.client import main"`, `_kill_tree` (taskkill /T /F) |
| `pdf_parser/ocr_fallback.py` | «OCR»-фасад | **тонкая обёртка над MinerU** (в докстринге прямо: NOT PaddleOCR/Tesseract); `needs_ocr` — порог 100 символов |
| `pdf_parser/gost_form_parser.py` | Геометрический парсер ГОСТ-формы | `GostFormParser.parse` (позиции `_pi.extract_text_with_positions`), `_apply_mothers` — наследование имён групп; **это уже частичный аналог mother-child из Hermes** |
| `pdf_parser/structurer.py` | Markdown → позиции | `SpecStructurer.structure`; regex `_fallback_parse`; опциональный LLM one-shot |
| `pdf_parser/review.py`, `review_dialog.py`, `feedback.py` | Ревью/правки | `SmartReview` (эвристика confidence), `ReviewDialog`, `FeedbackCollector` (SQLite) |
| `main.py` | GUI | `_load_pdf`, `_on_pdf_items_ready`, `_save_pdf_items_to_excel` (7 колонок) |
| `src/column_classifier.py`, `excel_writer.py` | Приём XLSX | `detect_columns(headers, value_rows)` → маппинг name/article/brand/spec/uom/qty/weight/position |

### 3.3 Факты о стеке (важно для плана)

- **OCR в приложении = MinerU 3.4** (subprocess, тяжёлый: layout-модели; живёт в общем venv). Быстрая классификация/экстракция — **pdf-inspector 1.17** (firecrawl, без зависимостей): `detect_pdf`/`process_pdf`/`extract_text_with_positions`.
- **PyMuPDF (fitz) и pdfplumber НЕ установлены** в venv (проверено). Значит текущий код не использует `find_tables` — табличная структура восстанавливается либо геометрически (positions, только ГОСТ-форма), либо из markdown (MinerU/pdf-inspector) регулярками.
- Тесты PDF-стека: `tests/test_pdf_parser.py`, `test_pdf_e2e.py`, `test_pdf_router.py`, `test_structurer_fixes.py`, фикстуры `tests/fixtures/pdf/`.
- Конфиг: `settings.yaml → pdf_parser: {fast_path: true, lang: east_slavic, method: auto, timeout: 300, use_llm: false, …}`.

### 3.4 Сильные стороны (переносим в новый инструмент без потерь)

1. QThread-поток + сигналы + аварийный Stop (kill-tree для OCR) — зрелая обвязка;
2. маршрутизация сканов: `detect_pdf` → `pages_needing_ocr`/порог текста → MinerU — «парсинг (OCR), затем обработка», как требует пользователь;
3. геометрический разбор ГОСТ-формы с матерями (`GostFormParser._apply_mothers`) — фундамент для общего mother-child;
4. `FeedbackCollector` — персистентные пользовательские правки (SQLite), применяются на каждом прогоне;
5. `ReviewDialog` — GUI-контроль качества (оставляем как элемент интерфейса);
6. продукт конвейера — XLSX → штатный `load_spec`/`detect_columns`, т.е. точка интеграции уже существует.

### 3.5 Слабые стороны vs эталон (что именно рефакторим)

| # | Проблема текущего механизма | Следствие | В Hermes-эталоне |
|---|------------------------------|-----------|------------------|
| A | Нет детекции границ спецификации: обрабатывается весь текст/весь PDF, включая титулы, ведомости, экспликации, штампы | мусор в позициях, «позиции» из чужих таблиц | `spec_header_score ≥ 6/9`, отсев NO_SPEC постранично |
| B | Markdown-поток (MinerU/pdf-inspector) — плоский текст; структура таблицы (колонки, объединённые ячейки, групповые строки) теряется | склейка/потеря строк, неверные qty/unit | `find_tables().extract()` с маппингом по тексту шапки, повёрнутые листы |
| C | Нет классификации строк: item/header раздела/component/continuation/группа | заголовки разделов приклеиваются к позициям или теряются | `classify()` + HEADER_PREFIXES + GROUP_INHERIT |

| F | LLM-структурирование — one-shot «текст → JSON» (use_llm=false по умолчанию) | нет итераций, нет верификации, нет правки правил | LLM-цикл: прогон → лог → верификация → правки → повтор |

| H | Нет QA-сканера и журнала обработки как артефакта | нечего проверять пользователю «по-гермесовски» | `_log.json` по каждой операции + QA-сканер |

## 4. Целевая архитектура нового инструмента

### 4.1 Принципы

1. **UI не меняется**: кнопка «📄 Загрузить PDF», прогресс, ReviewDialog, финальный XLSX → `load_spec`. Меняется движок под капотом.
2. **Старый код не удаляется**: переключатель `pdf_parser.pipeline: legacy | v2` в `settings.yaml`; до готовности v2 работает legacy; после — legacy отключается флагом и остаётся в дереве как бэкап (плюс git-тег перед переключением). Удаление — отдельным решением пользователя позже.
3. **Ядро — детерминированное, методология Hermes**: порт правил из `extract_spec.py` + референсов (spec-pdf-csv/pdf-table-to-csv), движок извлечения — PyMuPDF `find_tables()` (добавить `pymupdf` в requirements; лёгкий wheel, без нативных установок; pdf-inspector его не тянет — проверено). Геометрия pdf-inspector positions остаётся как fallback-источник для форм, где find_tables не справляется (ГОСТ-форма с объединёнными ячейками — уже работает).
4. **LLM-слой — «тот же LLM, что у Hermes»**: через существующий `llm_client`/`llm_providers` (routerai/opencode/локальные; креды из `~/.hermes/.env` и др. — тот же источник). Роль LLM — оркестратор и судья (см. 2.2), НЕ построчный экстрактор.
5. **Сканы — как раньше**: pdf-inspector detect → MinerU (OCR) → текст → тот же конвейер v2 (детекция спецификации работает по OCR-тексту/разметке). OCR-механизм не выкидываем — он часть «парсинг, затем обработка».
6. **Артефакты прогона** — как у Hermes: `data/pdf2spec/<spec>_log.json`, `final_rows.json`, QA-отчёт; пользователь видит и проверяет.

### 4.2 Пакет `src/pdf2spec/` (проект модулей, реализация — отдельными фазами)

| Модуль | Назначение | Источник методологии |
|--------|------------|----------------------|
| `extract.py` | Открытие PDF, страницы/повороты, `find_tables().extract()`, позиции; унификация в raw-records с `_page` | `extract_spec.extract_records`, `pdf-table-to-csv` (повёрнутые листы) |
| `spec_detect.py` | Детекция спецификации в проекте: `spec_header_score` ≥6/9, `_norm_cell` (мягкие переносы), FRAME/штампы, маппинг колонок по тексту шапки (не по индексу), отсев NO_SPEC постранично | `find_spec_header`, `map_columns`, `is_frame_row` |
| `row_classify.py` | Классификация строк: item / header (HEADER_PREFIXES ВК+ОВ, `[ВТК]\d`) / component (ГОСТ/ТУ/марка) / continuation / групповая (GROUP_INHERIT) | `classify`, шаблоны ВК/ОВ, доменные референсы |
| `fullname.py` | Правило полного наименования: поглощение матерей, перенос обозначений в «Тип, марка», наследование code/supplier/note, структурные подзаголовки | `hierarchical-parent-child-rows.md`, `gost_form_parser._apply_mothers` (адаптация существующего!) |
| `clean.py` | Чистка: split-слова (список SPLITS), Ø-токен-правила (`6<диам>х<толщ<100>`, `ф/∅`), «х», склейка ТУ/ГОСТ, `B1 .3`, ОВ-фитинги «стальной», ведущий «-» | `clean_text`/`clean_name`, доменные notes |
| `qa.py` | QA-сканер: orphan=0, артефакт-grep, счётчики ролей; журнал операций | `qa`, `qa_scan_csv.py` |
| `export_xlsx.py` | XLSX «как Hermes»: заголовки/колонки как в оригинале документа, одна строка = одна позиция, кириллица, форматирование | xlsx-правила сборки |
| `orchestrator.py` | LLM-цикл (см. 4.3) | механика Hermes (2.2) |
| `ocr.py` | Маршрут сканов: detect (`pages_needing_ocr`/порог текста) → MinerU → текст для v2 | текущий `runner.py`/`ocr_fallback.py` (переиспользование) |
| `runner_v2.py` | QThread с сигналами, идентичными `PdfParserRunner` (progress/items_ready/done, Stop) | текущий `runner.py` |
| `runtime_rules/` | JSON-правила, пополняемые LLM в рантайме: SPLITS, HEADER_PREFIXES, исключения — `data/pdf2spec/rules_*.json` (правки не в коде) | механизм «правка правил» Hermes |

### 4.3 LLM-оркестратор (ключевая часть «аналога»)

Цикл обработки одного PDF (внутри `runner_v2`, шаги не блокируют UI):

1. **Разведка** (детерминированно): страницы, повороты, есть ли таблицы; LLM-промайнинг не нужен — отчёт для человека.
2. **Прогон ядра**: detect → extract → classify → fullname → clean → qa. Детерминированный результат + `_log.json`.
3. **Верификация LLM**: оркестратор получает лог + подозрительные строки (requires_review из QA: orphans, неклассифицированные, низкий spec_score, конфликты матерей) и выносит решение по каждой (класс строки / мать-ребёнок / мусор / «не найдено таблиц»).
4. **Правка правил**: новые паттерны (неизвестный префикс раздела, новый split-фрагмент, новый Ø-вариант) LLM добавляет в `rules_*.json` (не в код) → повторный прогон ядра.
5. **Критерий останова**: QA чист (0 артефактов, 0 orphan) или лимит итераций (конфиг, напр. 3) → финальный XLSX.
6. **Отказоустойчивость**: LLM недоступен/ошибка/таймаут → детерминированный путь с пометкой `requires_review` (как сейчас SmartReview); circuit breaker — из `src/resilience.py`. LLM-запросы — компактные (решения по пачкам подозрительных строк, а не весь документ), лимит токенов на шаг.

Промпты строятся из методологии SKILL.md (разделы «Классификация», «Полное наименование», pitfalls) — это легитимное применение доменных правил, права на код не нарушаются.

### 4.4 Конфигурация и интеграция

- `settings.yaml`:
  ```yaml
  pdf_parser:
    pipeline: legacy        # legacy | v2 (переключение без удаления старого)
    v2:
      llm_review: true      # LLM-оркестратор вкл/выкл
      max_iterations: 3
      ocr: mineru           # маршрут сканов (как сегодня)
  ```
- `main.py`: точка входа `_load_pdf` создаёт `runner_v2` при `pipeline: v2` (сигналы те же → ReviewDialog/логика main не меняются).
- Продукт v2 (XLSX с колонками оригинала) → существующий `load_spec` + `detect_columns`; если маппинг не находит колонку (например «Завод-изготовитель») — дообучение `column_classifier` отдельной задачей (проверяется на фазе P2, см. 5).

### 4.5 Чего НЕ делаем

- Не переносим skills-документы в репозиторий как «набор для агента» (решение пользователя: не встраивать skills);
- не удаляем `src/pdf_parser/` и зависимости (`mineru`, `pdf-inspector`) — до отдельного решения;
- не меняем GUI и контракт сигналов;
- не пишем код в рамках этого плана.

## 5. Фазы реализации (ориентиры для будущих сессий; тесты финальной реализации — пользователь)

Каждая фаза: работа на ветке `feat/pdf2spec-*`, синтаксис `venv/Scripts/python.exe -m py_compile`, точечный pytest, запись в `state.md`, коммит только после подтверждения.

### P0 — Эталонные образцы и заморозка точки старта (до кода)
- Прогнать Hermes-ядро (`extract_spec.py`) на 2–3 реальных PDF: **ВК-проект целиком** (со спецификацией внутри) и **ОВ** (повёрнутые листы) — сохранить выходы (CSV/JSON/лог) как **golden-эталон** в `data/pdf2spec/golden/`.
- Зафиксировать: список правил/списков (HEADER_PREFIXES, SPLITS, MARKS, Ø-правила, шаблоны ВК/ОВ), которые придётся портировать.
- Создать бэкап-тег текущей рабочей базы (точка отката).

### P1 — Детерминированное ядро v2 (порт методологии)
- Модули `extract / spec_detect / row_classify / fullname / clean / qa`; движок — PyMuPDF (добавить `pymupdf` в requirements), геометрия ГОСТ — pdf-inspector positions (адаптация `GostFormParser`).
- **Критерий**: на golden-образцах выход v2 совпадает с выходом `extract_spec.py` пострóчно (сверка по `final_rows.json`); pytest на новых фикстурах (синтетика: Ø-коррупция, split-слова, повёрнутые листы, объединённые ячейки, проект-обёртка с ведомостями/экспликациями).

### P2 — Экспорт XLSX «как Hermes» + интеграция
- `export_xlsx.py`: колонки как в оригинале, одна строка = позиция, корректная кириллица/Ø, форматирование по образцу Hermes-сборки.
- Проверка приёма продукта штатным `load_spec`/`detect_columns`; при пробелах классификатора колонок — правки `column_classifier` (в рамках этой задачи, отдельным коммитом).

### P3 — LLM-оркестратор
- `orchestrator.py` + `runtime_rules/` + интеграция с `llm_client` (та же LLM, что Hermes: routerai/opencode/локальная — по настройке пользователя); промпты из методологии; лимиты итераций; fallback на детерминированный режим; верификация правок правил.
- **Критерий**: на новом PDF (не из golden) LLM-цикл доводит результат до QA-чистоты или честно помечает `requires_review`; недоступность LLM не роняет прогон.

### P4 — Сканы/OCR-маршрут
- `ocr.py`: detect → MinerU → текст → конвейер v2 (детекция спецификации по OCR-результату). Сравнение со старым structurer-путём на сканах (качество/полнота). OCR-механизм (MinerU/pdf-inspector) сохраняется — «парсинг, затем обработка».

### P5 — Переключение legacy → v2
- `pipeline: v2` по умолчанию; legacy отключается флагом (код не удалён); прогон всех GUI-состояний: пустой PDF, PDF без спецификации, проект без таблиц, Stop/ошибки, повторный запуск сессии.
- Финальные тестовые прогоны на реальных данных — **пользователь** (п.8 решений).

### P6 — Бэкап/чистка (только по отдельному решению пользователя)
- Решение по судьбе `src/pdf_parser/` (legacy), `mineru`/`pdf-inspector` в requirements, PDF-тестов старого стека; теги/ветки как архив.

## 6. Открытые вопросы и допущения (приняты по умолчанию, легко переиграть)

1. **«Та же LLM, что у Hermes»** — трактуем как: та же инфраструктура провайдеров/креденшиалов (уже в проекте) + выбор пользователем той же модели/провайдера в SettingsDialog, что стоит у Hermes (например routerai). Точную пару провайдер/модель для v2 зафиксировать при старте P3.
2. **Новая зависимость `pymupdf`** — лёгкий wheel (в духе «лёгкие pip-альтернативы»); без него ядро v2 не сможет использовать `find_tables()` (движок эталона). Если нежелательна — fallback-вариант: строить таблицы на pdf-inspector positions (как GostFormParser), но это больше кода и ниже качество на «не-ГОСТ» формах.
3. **Формат XLSX v2** (колонки оригинала) vs текущий 7-колоночный шим: после переключения `_save_pdf_items_to_excel` (старый шим) в v2-пути не используется; колонки «Поставщик/Масса/Примечание» доезжают до `load_spec` — при необходимости доучиваем `column_classifier`.
4. **ReviewDialog остаётся** (интерфейс не меняем): в v2 он показывает позиции с `requires_review` из QA/LLM-верификации вместо SmartReview-эвристики (SmartReview можно оставить как дополнительный источник).
5. **Правила, накопленные LLM в рантайме** (`rules_*.json`) — пользовательские данные (как feedback в SQLite): в git не коммитятся (как `data/`), при желании экспортируются.
6. План не затрагивает конвейер сбора цен (agent_loop и пр.) — точка стыка только `load_spec`.
