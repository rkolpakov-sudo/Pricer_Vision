# Полный план рефакторинга Pricer_Vision (v3 — архитектурная переделка подходов)

На основе анализа реального прогона (`runtime.log`, 137 позиций, ~54600 секунд) сформирован план из **16 изменений** (12 оригинальных + 5 новых, -1 отменён). Каждое изменение содержит: причину (подтверждённую логом), описание, решение, затрагиваемые модули, критерии качества и оценку влияния.

**Версия 1 плана была скорректирована по следующим фактам из лога (137 позиций, ~54600 секунд):**
- `penalized 58` — **опровержено**: реальность 1-4 за max_rounds (не 58)
- `mismatch 5-10 на позицию` — **завышено**: реальность 1 на позицию
- `session_facts` — **уже работает**: `♻️ Запрос-дубль` в логе = дедупликация через RowFacts
- Добавлены 5 проблемы, которых не было в v1: дубли запросов, неподходящие сайты, Яндекс dead-end, SPA wait, **архитектура подходов**
- **Критическая находка:** `get_approaches("unknown")` возвращает 200+ мусорных подходов — агент получает неподходящие подходы

## 🔴 КРИТИЧЕСКИЕ ИЗМЕНЕНИЯ (блокируют работу)

### Изменение №3. Разблокировка навигации при тупике (Anti-Deadlock)

**Причина (подтверждена логом):** Валидатор отвергает кандидата с `confidence < 0.6`, но система блокирует навигацию, требуя сначала сохранить этого кандидата. Агент попадает в бесконечный цикл.

**Факты из лога:**
- `🚫 Navigate blocked: price candidate seen on yandex.ru, not confirmed` (строка 365)
- `The system is blocking the transition to another site — first I need to save a price candidate from vseinstrumenti.ru.` (строка 99)
- 3 блокировки из 4 позиций (75%) — самая частая причина потерь времени
- Агент тратит 5-10 раундов на «дожимание» кандидата на мёртвом сайте

**Решение:**
1. Ввести правило: если `rounds_on_site > 5` и есть кандидат с `0.3 < confidence < 0.6`, то:
   - Принудительно сохранить кандидата с `requires_review: true` и причиной `forced_fallback`.
   - Сбросить флаг блокировки навигации.
   - Добавить в промпт инструкцию: *"Резервный кандидат сохранён. Переходи к следующему сайту для поиска более точного совпадения."*
2. Установить жёсткий лимит: **не более 2 попыток «дожать» кандидата на одном сайте**.

**Затрагиваемые модули:**
- `src/agent_loop.py:761-786` — логика блокировки навигации, счётчик попыток.
- `src/validator.py` — разрешение на сохранение `forced_fallback` при `rounds_on_site > 5`.

**Критерии качества:**
- Исчезновение записей `"Navigate blocked"` в логе.
- Время на позицию с тупиковым кандидатом: ≤120 сек (сейчас 500-700 сек).
- Метрика: `deadlock_rate = rows_with_navigate_blocked / total_rows` (цель: 0%).

**Влияние на качество агента:**
- ✅ Агент не застревает, а перебирает альтернативы.
- ⚠️ Риск: Сохранение неточных цен с `requires_review: true`.
- 🛡️ Митигация: Флаг `requires_review` гарантирует ручную проверку.

### Изменение №5. Fail-Fast для таймаутов Playwright

**Причина (подтверждена логом):** Агент тратит 10 сек на таймаут, затем LLM генерирует новый селектор, и цикл повторяется.

**Факты из лога:**
- 12 таймаутов `Timeout 10000ms exceeded` за 3.5 позиции (~3.5 на позицию)
- Таймауты на `browser_type` (строки 37, 209, 264, 387, 403, 479, 525, 536, 577, 620)
- Таймауты на `browser_click` (строки 24, 341, 423)
- Strict mode violations: `locator("input[name=\"search\"]") re...` (строки 37, 209, 536) — селектор совпадает с 3+ элементами

**Решение:**
1. Снизить таймаут для `browser_type` и `browser_click` до 3000 мс.
2. Ввести счётчик однотипных ошибок на уровне оркестратора.
3. Если `Timeout` происходит 2 раза подряд на одном сайте:
   - **Не передавать ошибку LLM.**
   - Автоматически вызвать `browser_evaluate` с универсальным JS-фолбэком:
     ```javascript
     () => {
       const inp = document.querySelector('input[type="search"], input[placeholder*="Поиск"], input[name*="search"]');
       if (inp) { inp.value = ''; inp.dispatchEvent(new Event('input')); return 'cleared'; }
       return 'no_input_found';
     }
     ```
   - Если фолбэк не работает — принудительный переход к следующему сайту.
4. При `strict mode violation`: fallback на `.first()` или JS-ввод через `browser_evaluate`.

**Затрагиваемые модули:**
- `src/mcp_bridge.py:298-299` — таймауты для инструментов.
- `src/agent_loop.py` — счётчик ошибок, логика фолбэка.

**Критерии качества:**
- Количество записей `"Timeout 10000ms exceeded"` в логе: ≤1 на позицию (сейчас 3.5).
- Время на обработку таймаутов: ≤6 сек (сейчас 35-40 сек).
- Метрика: `timeout_waste_seconds = total_timeout_time / total_rows` (цель: ≤10 сек).

### Изменение №12. Жёсткий hard cap 900 сек → 300 сек

**Причина (подтверждена логом):** Текущий hard cap 900 сек слишком мягок — агент может тратить 15 минут на одну позицию.

**Факты из лога:**
- Труба Ø86х3,0: **826.6 сек** (13.8 мин)
- Водомерный узел: **716.9 сек** (12 мин)
- ВСКМ-40 Ду32: **625.2 сек** (10.4 мин)
- Все три завершённые позиции >> 300 сек
- `Max rounds (40) reached` — лимит раундов, не времени

**Решение:**
1. Изменить `settings.yaml`: `row_hard_cap_seconds: 300`.
2. Если позиция не обработана за 300 сек — принудительное сохранение лучшего кандидата (если есть) с `requires_review: true` и переход к следующей позиции.

**Затрагиваемые модули:**
- `config/settings.yaml` — параметр `row_hard_cap_seconds`.
- `src/agent_loop.py` — логика принудительного сохранения при hard cap.

**Критерии качества:**
- Максимальное время на позицию: ≤300 сек (сейчас 625-826 сек).
- Метрика: `p95_row_time` (цель: ≤300 сек).

### Изменение №13. Duplicate query detection (НОВОЕ)

**Причина (подтверждена логом):** Агент повторяет запросы на одном сайте, получая таймауты и пустые результаты.

**Факты из лога:**
- 12+ дублей запросов за 4 позиции (строки 29, 109, 205, 213, 270, 392, 485, 531, 577, 626)
- Пример: `♻️ Запрос-дубль на santech.ru: «ВСКМ-40 Ду32»` → `♻️ Запрос-дубль на santech.ru: «ВСКМ-40»` → `♻️ Запрос-дубль на santech.ru: «ВСКМ»`
- Каждый дубль = 10-20 сек (таймаут + LLM-запрос)
- RowFacts уже détect les doublons (`♻️ Запрос-дубль`), mais l'agent les réduit au lieu de passer au site suivant

**Решение:**
1. В `RowFacts` добавить счётчик `query_attempts_per_site: Dict[str, List[str]]`.
2. Если агент пытается ввести запрос на сайте, где уже пробовал ≥2 варианта:
   - Вернуть ошибку: `"На этом сайте уже尝试ованы варианты: [список]. Переходи к следующему сайту."`
   - Не передавать ошибку LLM — принудительный переход.
3. При 3+ дублях на сайте — принудительный `site_switch` с `penalized += 1`.

**Затрагиваемые модули:**
- `src/session_facts.py` — `RowFacts`,新增 `query_attempts_per_site`.
- `src/agent_loop.py` — проверка дублей перед `browser_type`.

**Критерии качества:**
- Количество `"♻️ Запрос-дубль"` в логе: ≤1 на позицию (сейчас 3-4).
- Время, сэкономленное на дублях: ≤60 сек на позицию.

### Изменение №16. Архитектура подходов: (site, category) вместо (product_type, site) (НОВОЕ — КРИТИЧЕСКОЕ)

**Причина (подтверждена БД + логом):** Подходы хранятся по `(product_type, site)`, но `classify_product_type()` для большинства товаров возвращает `unknown`. `get_approaches("unknown")` возвращает **200+ мусорных подходов** (кабели, вентиляция, краны — всё подряд). Агент получает неподходящие подходы и тратит время на бесполезные действия.

**Факты из БД и лога:**
- В БД **500+ подходов**, из них **200+** привязаны к `product_type = unknown`
- `get_approaches("unknown")` возвращает подходы для **всех типов товаров** (трубы, кабели, вентиляция, арматура) — агент не может отличить релевантные
- 12 подходов из 72 вызовов `get_approaches` реально использовались (17%) — потому что при `unknown` возвращается мусор
- При этом `get_approaches_by_site("santech.ru")` работает — возвращает **60+ подходов** только для santech.ru, все релевантные

**Корневая ошибка:** Подходы привязаны к **конкретному типу товара** (`plumbing_heating_pipes`), а должны к **сайту + категории** (`santech.ru + pipes`). Товары одного типа (трубы) называются по-разному, но подход к сайту один и тот же.

**Решение:**
1. Новая модель хранения: `(site_id, category) → approaches` вместо `(product_type_id, site_id) → approaches`
   - `category` — общая категория: `pipes`, `valves`, `radiators`, `pumps`, `tools`, `ventilation`, `cables`
   - Маппинг `product_type → category` в `config/categories_and_sites.yaml`
2. `get_approaches(product_type, site)` → внутренне:
   - Шаг 1: `product_type → category` через маппинг
   - Шаг 2: `get_approaches_by_site_and_category(site, category)` — точный запрос
   - Шаг 3: Fallback `get_approaches_by_site(site)` — все подходы для сайта
3. При `product_type = unknown` — **всегда** fallback на `get_approaches_by_site(site)`
4. Обратная совместимость: старые `(product_type, site)` подходы мигрируются в новую модель при `build()`

**Пример:**
```
# Было:
get_approaches("unknown", "santech.ru") → 200+ мусорных подходов

# Стало:
classify_product_type("Труба Ø86х3,0") → "unknown"
get_approaches("unknown", "santech.ru"):
  1. unknown → category: ? (нет маппинга)
  2. get_approaches_by_site("santech.ru") → 60+ подходов для santech
  3. Фильтрация по категории (если известна) → релевантные
```

**Затрагиваемые модули:**
- `src/graph_engine.py` — `get_approaches()`, `save_approach()`, `build()`, новая таблица `approach_categories`
- `config/categories_and_sites.yaml` — маппинг `product_type → category`
- `src/agent_loop.py` — `_execute_graph_tool()`, вызов `get_approaches`

**Критерии качества:**
- `approach_relevance_rate = подходы_использованы / подходы_возвращены` (цель: ≥40%, сейчас 17%)
- `unknown_fallback_rate = подходы_найдены_через_fallback / total_unknown` (цель: ≥80%)
- Мусорных подходов при `unknown`: 0 (сейчас 200+)

**Влияние на качество агента:**
- ✅ Агент получает **релевантные** подходы даже для `unknown` товаров
- ✅ Подходы для сайта (сандтех.ру → сантехника) работают **всегда**, независимо от точного типа
- ⚠️ Риск: Потеря специфичных подходов (например, `plumbing_heating_pipes` vs `plumbing_heating_valves`)
- 🛡️ Митигация: Fallback `site + category` сохраняет специфику; `site` alone — запасной вариант

### Изменение №1. Иерархический поиск подходов в графе

**Причина (подтверждена БД):** Классификатор `classify_product_type()` возвращает `unknown` для большинства товаров. `get_approaches("unknown")` возвращает **200+ мусорных подходов** (кабели, вентиляция, краны — всё подряд). Агент получает неподходящие подходы.

**Факты из БД и лога:**
- В БД **500+ подходов**, из них **200+** привязаны к `product_type = unknown`
- `get_approaches("unknown")` возвращает подходы для **всех типов товаров** — агент не может отличить релевантные
- 12 подходов из 72 вызовов реально использовались (17%) — потому что при `unknown` возвращается мусор
- `get_approaches_by_site("santech.ru")` работает — возвращает **60+ подходов** только для santech.ru

**Решение:**
1. Трёхуровневый fallback в `get_approaches()`:
   - Уровень 1: точный `product_type` + `site`.
   - Уровень 2: `product_type` (все сайты).
   - Уровень 3: все подходы для данного `site` (универсальный).
2. При `product_type = unknown` — **всегда** fallback на `get_approaches_by_site(site)`.
3. Возвращать результаты с меткой уровня (`source_level: 1/2/3`).
4. Ранжировать по `success_count * freshness - consecutive_failures`.

**Затрагиваемые модули:**
- `src/graph_engine.py` — метод `get_approaches()`.
- `src/agent_loop.py` — функция `_execute_graph_tool()`.

**Критерии качества:**
- `approach_relevance_rate = подходы_использованы / подходы_возвращены` (цель: ≥40%, сейчас 17%).
- Мусорных подходов при `unknown`: 0 (сейчас 200+).

### Изменение №4. Агрессивное сжатие контекста (Rolling Window + Summary)

**Причина (подтверждена логом):** Агент копит до 91 сообщения. Prompt пик 23к токенов. Модель «теряется».

**Факты из лога:**
- `Context trim: 43584 → 11772 tokens (kept 14 of 77 messages)` (строка 175)
- `prompt=23063 completion=478` (строка 181) — пик промпта
- `prompt=21559 completion=763` (строка 176) — второй пик
- 20+ событий trim за 4 позиции
- После trim остаётся 11-15к токенов — модель всё ещё получает огромный контекст

**Решение:**
1. Жёсткая структура `messages`:
   - Всегда хранить: System Prompt + Initial Context (товар + подсказки).
   - Хранить **последние 3 пары** (tool_call + result).
   - Всё предыдущее заменять на **одно сводное сообщение** от системы:
     ```
     РЕЗЮМЕ РАУНДОВ 1-15:
     - Сайт santech.ru: 16 раундов, таймауты поиска, переход заблокирован.
     - Сайт dn.ru: 3 раунда, Navigate blocked ×2, прямой URL не сработал.
     - Текущая стратегия: переход к yandex.ru.
     - Ключевые факты: URL карточки на dn.ru = https://...
     ```
2. Критичные факты (найденные URL, селекторы, артикулы) сохранять в `session_facts` (in-memory dict).

**Затрагиваемые модули:**
- `src/agent_loop.py:2266-2309` — логика trim, агрегация истории.
- `src/session_facts.py` — хранение `session_facts`.

**Критерии качества:**
- Размер промпта стабилен: 4000-6000 токенов (сейчас 10-23к).
- Метрика: `avg_prompt_tokens` (цель: ≤6000).

### Изменение №14. Wrong site skip (НОВОЕ)

**Причина (подтверждена логом):** Агент тратит раунды на заведомо неподходящие сайты.

**Факты из лога:**
- `tinko.ru` (охранная техника) для водомерных узлов — 5 раундов, 0 результатов (строка 474-516)
- `ridan.ru` (тепловая автоматика) для счётчиков воды — агент пропускает (строка 520), но потом возвращается (строка 568)
- `pulsar-msk.ru` (производитель счётчиков) для ВСКМ-40 — 16 раундов, force switch (строка 470)

**Решение:**
1. В `config/categories_and_sites.yaml` добавить поле `incompatible_types` для каждого сайта:
   ```yaml
   tinko.ru:
     incompatible_types: [water_meters, pipe_fittings]
   ridan.ru:
     incompatible_types: [water_meters, filters]
   ```
2. При выборе сайта проверять `incompatible_types` — если `product_type` в списке, пропускать сайт без навигации.
3. При `force_switch` — penalized подходы для этого сайта + пометка `site_incompatible` для данного `product_type`.

**Затрагиваемые модули:**
- `config/categories_and_sites.yaml` — поле `incompatible_types`.
- `src/agent_loop.py` — фильтрация сайтов перед навигацией.

**Критерии качества:**
- Количество посещений неподходящих сайтов: 0 (сейчас 2 из 4 позиций).

### Изменение №15. Yandex dead-end (НОВОЕ)

**Причина (подтверждена логом):** Агент ищет через Яндекс, кликает по ссылкам, не может перейти на сайт.

**Факты из лога:**
- `🌐 Открываю https://yandex.ru/search/?text=водомерный%20узел%20купить` (строка 337)
- `👆 Клик по элементу e905415 → error: click failed: Timeout 10000ms exceeded` (строка 341)
- `Вкладок нет — клик не перешёл` (строка 359)
- `🚫 Navigate blocked: price candidate seen on yandex.ru, not confirmed` (строка 365)
- 4 раунда, 30-45 сек впустую

**Решение:**
1. Запретить `browser_navigate` на `yandex.ru/search` — вернуть ошибку: `"Яндекс-поиск запрещён. Используй прямые URL магазинов."`
2. Разрешить `browser_navigate` на `yandex.ru` только для проверки已知 URL (не для поиска).
3. При попытке — автоматический переход к следующему сайту из списка.

**Затрагиваемые модули:**
- `src/agent_loop.py` — фильтрация URL перед `browser_navigate`.

**Критерии качества:**
- Количество навигаций на `yandex.ru/search`: 0 (сейчас 1 из 4 позиций).

## 🟢 СРЕДНЕПРИОРИТЕТНЫЕ ИЗМЕНЕНИЯ (оптимизации)

### Изменение №2. Раздельный учёт неудач по паре (approach_id, product_type)

**Причина (опровержена логом):** План утверждал `penalized 58 approaches` за max_rounds. Реальность: **penalized 1-4**.

**Факты из лога:**
- `📉 Force switch: penalized 4 approaches` (строка 471) — 4 подхода на pulsar-msk.ru
- `📉 Max rounds: penalized 1 approaches` (строка 558) — 1 подход на santech.ru
- Массовой деградации НЕТ — проблема завышена

**Решение (упрощённое):**
1. При `force_switch` penalize только подходы, которые **реально использовались** в текущей сессии (отслеживать по `steps`), а не все подходы на сайте.
2. Отдельная таблица `approach_product_stats` — опционально, при необходимости.

**Затрагиваемые модули:**
- `src/agent_loop.py` — фильтрация penalize по реально использованным подходам.

**Критерии качества:**
- Количество `penalized` при max_rounds: ≤2 (сейчас 1-4 — уже нормально).

### Изменение №7. Семантическая проверка Product Mismatch

**Причина (завышена в плане):** План утверждал 5-10 mismatch на позицию. Реальность: **1 на позицию**.

**Факты из лога:**
- `⚠️ Product mismatch — advisory: spec=... vs found=...` (строки 95, 170)
- `LLM confirm override REJECTED for mismatched product (conf 0.30 < 0.60)` (строка 170)
- 2 REJECTED подряд — проблема реальна, но не массовая

**Решение (упрощённое):**
1. Нормализовать единицы: `Ø` = `Дн` = `DN` = `мм`.
2. Если ключевые атрибуты (тип, диаметр, бренд) совпадают — повышать `confidence` до 0.7.
3. Без создания отдельного модуля `product_normalizer.py` — встроить в `validator.py`.

**Затрагиваемые модули:**
- `src/validator.py` — семантическая проверка.

**Критерии качества:**
- Количество `REJECTED` из-за mismatch: ≤1 на позицию (сейчас 1-2).

### Изменение №9. Нормализация токенов для confirmed_prices

**Причина (подтверждена логом):** Токен-матчинг не учитывает варианты написания.

   - **Откат:** Увеличить лимит дублей до 3.
